What the app does

AI Coach is a conversational practice tool: a user picks one of three coaching modes — psy (emotional intelligence, self-awareness), professional (career, negotiation, interviews), or sport (performance mindset, focus) — and has a back-and-forth text conversation with an LLM playing that coach persona. The user can also speak into a microphone; audio is transcribed to text via a local Whisper model before being sent as a normal message. At the end of a session the user can request a coaching report summarizing the conversation.

The core loop is: sign in → pick a mode → have a conversation → end the session and get a report. Five scripted role-play scenarios (job interview, salary negotiation, etc.) exist as JSON files with rich system prompts, and a 603-document coaching knowledge base has been collected and embedded — but neither is wired into the live conversation flow yet (see Known Gaps in later tabs).

Audio recording flow (step-by-step)

1
User taps the mic button in InputBar → ConversationPage.handleMicToggle() calls useAudioRecorder.start().
2
navigator.mediaDevices.getUserMedia({'{'}audio:true{'}'}) requests mic permission; a MediaRecorder is created with mimeType: "audio/webm" and started.
3
While recording, InputBar swaps its textarea for WaveformViz (ambient animation — no live analyser is attached yet).
4
User taps stop → recorder's onstop handler assembles the collected chunks into a single Blob and stops all media tracks.
5
transcribing is set true; the blob is uploaded via messageApi.transcribeAudio() to POST /transcribe/ as multipart form data.
6
Backend runs faster-whisper and returns {'{'} transcript {'}'}. The hook's onTranscript callback appends the text into the (controlled) input value in ConversationPage.
7
User reviews the transcribed text in the input box and presses send like any normal text message — voice never bypasses the text send path.

Authentication flow

Email registration (3 steps)

1
POST /auth/send-code — rejects if the email is already a registered User; upserts a PendingVerification row with a bcrypt-hashed 6-digit code (10 min TTL) and emails it.
2
POST /auth/verify-code — checks the code (max 5 attempts), marks the row verified, issues a signup token (JWT, 5 min TTL, type: "signup").
3
POST /auth/complete-signup — decodes the signup token, requires the pending row still exists and is verified, creates the User, deletes the pending row, issues access + refresh tokens.

Google OAuth

1
Frontend redirects the browser to GET /auth/google/login, which redirects again to Google's consent screen.
2
Google redirects back to GET /auth/google/callback?code=...; the backend exchanges the code for a Google access token, then fetches userinfo.
3
Looks up the user by google_id, falling back to matching by email (linking the Google id to an existing password account) or creating a brand-new user.
4
Issues access+refresh tokens and redirects to {'{'}frontend{'}'}/oauth-success#token=...; the refresh token is also set as an httpOnly cookie.

Access token

15 minutes · sent as Authorization: Bearer · JWT type: "access"

Refresh token

7 days · httpOnly cookie scoped to /auth · rotated on every /auth/refresh call

Signup token

5 minutes · proves "this email was just verified" between steps 2 and 3 of registration

LLM integration

llm_service.py uses the OpenAI Python SDK pointed at a custom base_url (https://tokenfactory.esprit.tn/api), calling model hosted_vllm/Llama-3.1-70B-Instruct.

SYSTEM_PROMPTS = {
  "psy":          "You are an empathetic psychology coach...",
  "professional": "You are a sharp professional coach...",
  "sport":        "You are a sport performance coach...",
}

get_coach_response(mode, history, user_message):
    messages = [system_prompt] + history[-20:] + [user_message]
    → client.chat.completions.create(model=MODEL, temperature=0.7, max_tokens=512, ...)

Context window management: the last 20 messages of a conversation are fetched from SQLite and passed as chat history on every turn (constant defined independently in both llm_service.py and messages.py as CONTEXT_WINDOW = 20). There is no summarization or truncation strategy beyond this hard cutoff.

Where RAG will plug in: nowhere yet. rag_engine.py is an empty file, and get_coach_response() builds its message list purely from the system prompt + raw history — no retrieval step exists. The intended integration point (per the RAG tab) is to embed the user's message, query coaching_kb filtered by mode, and splice the retrieved chunks into the system prompt before the history.

The backfill story

192 legacy documents (collected before the current pipeline scripts existed) were missing tier/language metadata entirely. This was surfaced by audit_collection.py's tier/mode matrix and fixed retroactively with backfill_legacy_metadata.py, which normalized the older records in place. The newer collector scripts (collect_session_sources.py, collect_pubmed_openaccess.py) write the full 6-field schema from the start, so this class of gap shouldn't recur for future collection runs.

Emotion classifier

Architecture: ACNN (an attention/CNN-style network) trained on RAVDESS (Ryerson Audio-Visual Database of Emotional Speech and Song).

Detects: a fixed set of emotion classes from RAVDESS (typically calm, happy, sad, angry, fearful, surprised, disgust, neutral).

Where the weights live: a trained .pkl checkpoint, intended to be loaded by services/emotion_model.py — which is currently an empty file, so nothing loads it in the running backend yet.

How it will integrate

1
Incoming audio chunk (same one used for transcription).
2
Convert to a mel spectrogram.
3
Feed through the ACNN checkpoint.
4
Output an emotion label + confidence score, to be written into Message.emotion.

Flow 1 — User sends a text message

1
User types in InputBar.jsx and presses Enter / clicks send.
2
messageApi.sendMessage() → POST /conversations/{'{'}id{'}'}/messages
3
Request is handled by conversations.py's route (registered first — see the routing note in the Backend tab), which saves the user message to SQLite.
4
Builds message history from SQLite and calls its local _get_ai_response() placeholder — not llm_service.get_coach_response() — returning a fixed template string.
5
Saves the assistant message, returns it, messageStore updates, MessageList.jsx re-renders.
The design intent (visible in messages.py, which is fully wired to llm_service.py) is clearly for this flow to hit the real LLM. Swapping the router registration order in main.py — or removing the duplicate placeholder route from conversations.py — would make that the actual behavior.

Flow 2 — User records voice

1
User taps the mic → useAudioRecorder hook.
2
getUserMedia → MediaRecorder records audio/webm.
3
User taps stop → a Blob is created from the recorded chunks.
4
POST /transcribe/ → faster-whisper processes the audio.
5
Transcript returned, fills the InputBar textarea; user reviews and sends it like any text message.
Future: the same audio would also feed the emotion CNN + librosa feature extraction to populate the vocal-metric columns on Message.

Flow 3 — Coaching report generation (current basic implementation)

1
User clicks "End & get report" in ConvTopbar — currently only console.log("end session"), not yet calling the backend.
2
Once wired: POST /conversations/{'{'}id{'}'}/end → conversations.py router.
3
Counts user/assistant messages for the conversation (no LLM call is made).
4
Saves a CoachingReport row with a templated summary and placeholder strengths/growth-area lists.
5
Returns the report; ReportPage.jsx would display it — today it just shows a static "coming in M6" message instead.

Flow 4 — RAG-enhanced response (planned, not yet implemented)

1
User message arrives; mode is read from the conversation record.
2
Query ChromaDB: embed the user message with multilingual-e5-base ("query: " prefix).
3
Retrieve top-5 chunks filtered by mode + a relevant tier (e.g. technique for suggestions, session_guide for tone).
4
Inject retrieved chunks into the LLM system prompt as grounding context.
5
Llama 3.1 70B generates a response informed by the coaching knowledge base.
6
Further out: also inject live vocal/body signal data into the prompt once the speech pipeline populates those fields.
